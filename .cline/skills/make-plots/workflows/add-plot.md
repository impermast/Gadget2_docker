# Workflow: add a plot to the supported pool

Adding a plot is an exception to the render-only workflow and a scoped code change. The goal is one coherent registry, not another one-off script or near-duplicate.

1. **Search before implementing.** Read `nbody/analysis/REGISTRY.md` and search the code for plots with the same scientific question/data source. If an existing entry can answer the request via config, reuse it. If it is an extension of an existing plot, prefer extending that implementation rather than registering a near-copy. State the distinction and proposed registry name before coding if duplication risk is unclear.
2. **Agree on scientific contract.** Establish plot purpose, input block, data source/loader, required fields, units, output filename, and what scientific transformations are permitted. Do not infer a new estimator, threshold, or interpretation from a visual request; clarify scientific choices with the user.
3. **Reuse the canonical structure.** Put the class in the existing relevant module under `nbody/scripts/analysis/plots/`; do not create one Python file per figure without a module-level reason. Use `BasePlot`, `data_contract`, `default_config`, and `@register`. Data access and calculations belong in the existing loader layer. Plot classes render already prepared data and do not open snapshots/HDF5.
4. **Keep design global.** Use shared `PlotSettings`/`style.py` for fonts, palette, line widths, grid, sizing and export. Add only plot-semantic defaults to this plot's `default_config` (for example log axes or an appropriate sequential/diverging map). Do not copy global colors/sizes or hard-code one-off cosmetics. If the shared policy cannot express a needed choice, make a separate, explicit shared-style change via `workflows/style.md`.
5. **Integrate the runner minimally.** Prefer adding the plot to an existing block runner. Add a new runner only if the input/selection/execution contract genuinely differs; register its path on the plot and follow `AnalysisPaths`. No custom output paths, duplicate scripts, or alternate artifact trees.
6. **Test and publish metadata.** Add synthetic loader/render coverage for valid data, contract failures, output naming and any new mode. Run focused `math`, `render`, and `guard` tests. Regenerate `nbody/analysis/REGISTRY.md` using `registry_docs.py` and verify `--check`; never edit generated Markdown manually. Confirm the registry contains exactly one entry for this purpose and its runner/file/config fields are correct.
7. **Review scope and output.** Inspect the diff for unrelated user changes; do not include them. Do not render production data or overwrite existing outputs unless separately authorized. Report the new registry entry, reuse/duplication decision, implementation files, tests, and any unresolved scientific assumptions.
